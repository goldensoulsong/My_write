# HTML 的不合理无效性

> **副标题**：在 AI 工作流里用 HTML 替代 Markdown 是一种倒退
> **原作者**：Kurtis Redux
> **原文**：[The Unreasonable Ineffectiveness of HTML](https://kurtis-redux.medium.com/the-unreasonable-ineffectiveness-of-html-5bd01ae1e879)

上周，Claude Code 圈内人 Thariq 写的一篇文章《Using Claude Code: The Unreasonable Effectiveness of HTML》在开发者社区点燃了激烈讨论。

那篇文章主张：HTML——而非 markdown——应当成为人和 AI 交互的基础格式。作者列举了一连串理由和取舍。

但我认为这种 markdown-bashing 立场并不成立，里面混着不少误解。下面我把原文的核心论点压缩翻译，再附上我的看法。

原文较长，但围绕的核心其实只有一句：随着 AI 能力提升，markdown 已成瓶颈。人 - Agent 工作流（比如 Claude Code）应当整体转向 HTML，以追求更高的信息密度、更好的视觉清晰度、更丰富的交互能力。

## 1. 信息密度与表达力

**原文论点**：
HTML 能传达的信息远多于 markdown。它不只是文字，CSS 可以做样式、SVG 可以画图。这干净地替代了 markdown 里那种笨拙的 ASCII 艺术。

**我的看法：复杂不等于高效。内容和表现要分离。**

markdown 的核心哲学恰恰是**内容与表现分离**。它强迫 AI 和人都把注意力放在逻辑和文本上。

让 AI 生成那些塞满标签、内联 CSS、SVG path 的 HTML，等于邀请大量样板噪音进来。而现代 markdown 在需要时也能渲染 HTML，并且和 Mermaid、PlantUML 这类声明式图表工具集成得很好。那些语法干净得多，人也容易编辑得多。

## 2. 视觉清晰度与可读性

**原文论点**：
没人愿意仔细读 100 行以上的 markdown。HTML 可以用 tab、accordion、响应式布局组织复杂的系统设计或代码逻辑。

**我的看法：真正重要的可读性，是源码可读性。**

HTML 只有渲染后才好读，它的源码本身对人眼是敌意的。markdown 不论是否渲染，都有强烈的内在结构和可读性——这对长期生活在终端和编辑器里的知识工作者至关重要。**写作，不论是文字还是代码，本身就是思考的一部分。**

现在有一种越来越流行的观点：人不需要再读源了，AI 来写、来报告、甚至 vibe coding。但**如果你停止读源，你就在外包你的思考**。一旦我们集体放弃读源，我们就放弃了对它进行推理的能力——只能对着 AI 输出的漂亮东西傻笑。这种趋势我们已经在看见。

## 3. 分享

**原文论点**：
markdown 缺乏浏览器原生渲染，常常得当附件发。HTML 可以上传到 S3，链接一发，同事到处都能打开——更高效。

**我的看法：这增加了基础设施依赖和安全风险。**

实际操作中，HTML 不那么容易分享。任何超出 trivial 程度的 HTML 都需要正经的托管（S3、Vercel 之类）。这增加了基础设施成本，也带来权限和数据泄露的担忧。

反过来，markdown 是现代协作的通用语。粘进 GitHub、GitLab、Notion、Slack 都能原生渲染——不需要"上传文件、生成链接"这套繁文缛节。

我推荐过很多带渲染功能的 markdown 编辑器，连 Windows 记事本现在都支持 markdown。markdown 是默认的新文本格式。很难想象 2026 年还有正经知识工作者打不开 markdown 文件。

## 4. 双向交互与自定义编辑器

**原文论点**：
HTML 支持双向交互。当文本框不够用时，可以让 AI 生成一次性编辑器（比如可拖拽看板、feature flag 表单），调到满意，再把数据导出回 AI。

**我的看法：过度工程，且是安全雷区。**

让 AI 临场拼出一个带 JS 的界面是过度工程。

- 跑未经审计的、AI 生成的 JS 有 XSS 或本地数据泄露风险。**读文本变成了运行代码**。
- 生成的交互逻辑常带边角 bug。我们真的要花时间 debug 一次性工具吗？把核心问题用纯文本解决通常更好。这种做法说白了就是在抛光一坨垃圾。

## 5. 生成速度与 token 成本

**原文论点**：
HTML 生成慢 2-4 倍，用更多 token，但有了百万级 context window，这点成本无足轻重，结果值这个钱。

**我的看法：它稀释了注意力——人和 AI 的都稀释。**

假设它"只是"慢 2-4 倍，假设算力提升让一年后这看起来微不足道。在交互式 AI 工作流里，这个延迟是灾难性的。等几分钟看一份花哨报告会摧毁心流。

更糟的是，即便有大 context window，喷出大量冗余 HTML token 也会**稀释模型的注意力**，让它在长输出里更容易跑题，幻觉风险更高。当然，输出 token 多了，API 账单也更贵。

这一切本来根本没必要。

## 6. 审查与版本控制

**原文论点**：
这是最大的缺点。HTML 的 diff 噪音多，比 markdown 难审查。

**我的看法：审不了的东西就是玩具。**

作者对此一笔带过，但**审查和版本管理——尤其是人工审查——是认真生产力的红线**。

审查意味着真的去读、去理解，有时辅以工具（合适场合用 diff，更多时候是非代码文档的细心审阅）。如果一份东西没法干净审查，它就嵌不进合规的企业工作流，也无法在运营层面规模化。它会停留在浅层的、玩具化的用法上——花哨、好玩，但新鲜感一过就没意义。

Claude Code 是真正的生产力软件。为什么要往 AI 玩具的方向赛跑？

## 总结

《HTML 的不合理有效性》确实展示了 AI 在前端生成上的强大。HTML 也确实能做出炫酷的 demo——以及，是的，吸引人的 AI 玩具。

但 markdown 是知识工作的基石。

把日常交互里的 markdown 换成 HTML，是用视觉光鲜换掉了源码可读性、安全性、生态兼容性、可审性。

在真正的生产力场景里，这不专业——这是开倒车。无论 AI 怎么接进我们的工作流，赢的策略始终是**保持简单、内容优先**。这是这些年里一直对我管用的东西。
