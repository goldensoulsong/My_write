## 引言

Markdown 已经成为 Agent 与人之间最主流的输出格式。它简单、便携、能做基础富文本，编辑起来也很容易。Claude 甚至能用 ASCII 在 markdown 里画出意外能看的图。

但随着 Agent 能力越来越强，我发现 markdown 的限制越来越明显。

具体地说：

- 我读不下超过 100 行的 markdown 文件
- 我希望 Claude 能生成更丰富的可视化、配色和图表
- 我希望生成的内容能更方便地分享出去

而且，我现在已经基本不亲手编辑这些文件了。它们更多是被当作 spec 或参考文档使用。我做修改的时候，也是用 Claude 来改——这把 markdown 最大的好处之一（人手编辑友好）抹掉了。

所以我开始用 HTML 替代 markdown 作为输出格式，团队里越来越多人也在这么做。这篇文章讲我们为什么、以及怎么用 HTML 让 Claude Code 的输出更丰富、更易读。

## 为什么用 HTML

### 信息密度

HTML 能承载的信息密度远超 markdown。除了基础的标题和格式之外，它还能：

- 用表格表达表格化数据
- 用 CSS 表达设计信息
- 用 SVG 画图
- 用 script 标签嵌代码
- 用 HTML + JS + CSS 表达交互
- 用 SVG + HTML 表达工作流
- 用绝对定位和 canvas 表达空间数据
- 用 image 标签嵌图片

我的看法是：几乎没有什么信息是 Claude 能读但不能用 HTML 高效表达的。这让 HTML 成为一种非常高效的双向沟通介质——模型把深度信息传给你，你也能高效审阅。

否则模型只能在 markdown 里做一些低效的事情，比如 ASCII 图，或者用 unicode 字符近似配色（我个人最爱的一种）。

### 视觉清晰度和阅读舒适度

Claude 能处理的工作越来越复杂，写出来的 spec 和计划也越来越长。100 行以上的 markdown 我自己都读不下，更别想让组织里其他人读完。

HTML 文档读起来轻松得多——Claude 可以用 tab、插图、链接来组织视觉结构，甚至做成 mobile-responsive 让你不同设备上不同体验。

### 分享便利

markdown 文件不太好分享——大多数浏览器并不能很好地原生渲染。你常常得作为附件丢进邮件或聊天里。

HTML 只要上传一份，链接发出去就行。同事在哪里都能打开，方便引用。

你的 spec、报告、PR 描述，被人真的读到的概率会高得多。

### 双向交互

HTML 还可以让你和文档[直接交互](https://x.com/trq212/status/2017024445244924382)。比如让它生成滑块、旋钮，调整某个设计或算法参数看效果。还可以让它把这些调整变成可粘贴回 Claude Code 的 prompt。

需要时，这相当于为当前问题创建一个临时的、专属的编辑环境。

### 数据接入

用 Claude Code 而不是 Claude.ai 或 Claude Design 生成 HTML 的最大好处之一，是 Claude Code 能接入的上下文更多。

写这篇文章时，我让 Claude Code 读我整个代码文件夹，找出所有我生成过的 HTML 文件，分组归类，然后做一份带图的 HTML 总览。文章里的那些图就是这么来的。

除了文件系统，Claude Code 还能通过 MCP（Slack、Linear 等）、浏览器（Claude in Chrome）、git 历史拿到更多上下文。

## 怎么开始

不需要什么特别配置。你直接 prompt "做一个 HTML 文件" 或 "做一个 HTML artifact" 就行。

关键是知道你想要的产物是什么、要做什么用。重复出现的模式可以慢慢沉淀成 skill，但一开始从零 prompt 是最好的入门方式。

## 用例

### Spec、规划、探索

HTML 是 Claude 处理问题的一块富画布。我开始一个新问题时，期待的不是单一 markdown 计划，而是一组互相链接的 HTML 文件。

比如先让它头脑风暴几种不同方向，画几个 mockup；选定一个方向后让它扩展、写实施计划；满意之后开新会话把所有这些文件传进去做实施。

验证阶段同样可以让 verifier agent 读这些文件，它就能拿到非常完整的上下文。

示例 prompt：

- 我不确定 onboarding 屏幕该怎么做。生成 6 种风格差异明显的方案——layout、调性、密度都要不同——放在同一个 HTML 文件里以网格排布，方便对比。每种方案标注它的取舍。
- 写一个完整的实施计划 HTML 文件，附 mockup、数据流图、关键代码片段。要让它读起来好消化。

适用场景：探索代码实现的不同方向、并行尝试多个视觉设计。

### 代码审查与理解

代码在 markdown 里很难读。HTML 能渲染 diff、注释、流程图、模块图。

示例 prompt：

帮我审查这个 PR，做一个 HTML 描述它。我对其中的 streaming/backpressure 部分不熟，重点讲那块。渲染真实 diff，行内加注释，按严重程度配色，加任何能帮我理解概念的元素。

适用场景：写 PR、审 PR、理解某段代码。

### 设计与原型

Claude Design 本身就建立在 HTML 之上，因为 HTML 在表达设计上极强，哪怕你的最终落地是 React 或 Swift，Claude 也可以先用 HTML 做出 sketch，再转译。

也可以用来原型化交互——动画、动作。让 Claude 加滑块、旋钮，调出你想要的精确感觉。

示例 prompt：

我想原型化一个新的 checkout 按钮，点击后播放动画并快速变紫。做一个 HTML 文件，带几个滑块和选项让我尝试不同动画参数，加复制按钮把好用的参数复制走。

适用场景：设计系统物料、调整组件、可视化组件库、动画原型。

### 报告、研究、学习

Claude Code 非常擅长跨多源整合信息生成易读报告。可以让它搜你的 Slack、代码库、git 历史、互联网，做成长 HTML 报告、交互式 explainer，甚至幻灯片。

让它用 SVG 做图来辅助说明。

示例 prompt：

我搞不清我们的 rate limiter 实际怎么工作。读一下相关代码，做一个 HTML explainer：token bucket 流程图、3-4 个加注释的关键代码片段、底部一个 "gotchas" 区。要为只看一次的人优化。

适用场景：feature 总结、explainer、周报、事故报告、SVG 图与流程图。

### 自定义编辑界面

有时纯文本框无法表达你想要什么。这种情况下我会让 Claude 做一个一次性编辑器——不是产品，不是可复用工具，就是为这一份数据专门做的一个 HTML。

诀窍永远是结尾要有一个导出："copy as JSON" 或 "copy as prompt"，把你在 UI 上做的操作变回可以贴进 Claude Code 或提交进文件的东西。**你还在循环里，但这个循环紧得多。**

示例 prompt：

- 我要重排 30 个 Linear ticket。做一个 HTML 文件，每个 ticket 是可拖拽卡片，分到 Now / Next / Later / Cut 四列。先按你最佳猜测排好。加 "copy as Markdown" 按钮，导出最终顺序，每桶给一行简要理由。
- 这是我们的 feature flag 配置。给我做一个表单编辑器，按域分组，显示 flag 之间的依赖。如果我打开了某个 flag 但它的前置 flag 没开就警告我。加 "copy diff" 按钮，只导出改动的字段。
- 我在调一个 system prompt。做一个并排编辑器：左边可编辑 prompt，变量槽位高亮；右边三个示例输入实时渲染填充模板。加字符/token 计数和复制按钮。

适用场景：重排 / 分类 / 分桶任何东西（ticket、test case、反馈）；编辑结构化配置；调 prompt 或模板配实时预览；策划数据集；标注文档；挑那些用文字说不清的值（颜色、缓动曲线、裁剪区域、cron、正则）。

## 常见问题

**这样不会更费 token 吗？**
markdown 确实更省 token。但 HTML 的表达力和我真的会去读它的概率，加起来给的整体回报更高。Opus 4.7 一百万的 context window 下，多出来的 token 在上下文里也基本不影响。

**你现在还会用 markdown 吗？**
基本上不用了。我承认我在 HTML 极端主义这一侧。

**这是不是替代了 planning？**
我现在不是单一 plan，而是为不同阶段做不同 HTML 文件。比如实施计划一份、UI 探索一份、最后再做一份组件总览。这些文件我会留着做参考、做验证。

## 留在 Claude 的循环里

最后总结，我用 HTML 替代 markdown 的真正原因——**它让我感觉自己还在 Claude 的循环里**。

Claude 接管的事情越多，我越发现自己不再仔细读 plan。我想要一种方式让自己继续参与到它的选择里，而不只是把任务甩给它。HTML 正好是这个东西。

我现在感觉比以前任何时候都更 in-the-loop。
