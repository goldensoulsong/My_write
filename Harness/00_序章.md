# 序章：一个 GBDT 模型教会我的事——Agency 来自模型，Agent = 模型 + Harness

在翻开任何一行开源代码之前，我想先讲一个自己的故事。

## 我做过的一个电价预测项目

之前我接过一个 AI4S（AI for Science）项目：**电价预测与收益最大化**。

任务很直接——根据历史数据预测未来的电力市场价格，然后在约束条件下做出"低买高卖"的决策，让收益最大化。听起来很复杂对吧？电力市场本身就是一个受天气、负荷、政策、季节等多重因素交织影响的混沌系统。

但实际上，我做的事情非常简单：

1. **数据**：收集过去一年的逐时天气数据（温度、湿度、风速、光照等）和对应的电价数据。
2. **模型**：用了一个 **GBDT（Gradient Boosted Decision Trees）**。没有深度学习，没有 Transformer，没有任何花哨的架构。就是一个梯度提升决策树。
3. **决策**：把预测出的未来电价送进一个简单的优化环境——在给定的储能容量和功率约束下，模型自动学会了什么时候该买电、什么时候该卖电。

结果？**效果出奇地好。**

我没有手写一大堆"当电价低于某个阈值就买入"之类的 if-else 规则。没有精心设计复杂的约束求解器。没有堆叠一层又一层的规则引擎。我只是把合适的数据喂给了一个合适的模型，再把模型放进了一个定义好行动空间的环境里。模型自己学会了识别天气模式和电价之间的关系，学会了在约束范围内找到收益最大的操作策略。

**一个简单的 GBDT，放进一个定义好的环境，就能做出比手工规则优秀得多的决策。**

这件事给我的冲击非常大。

## 这件事和 Agent 有什么关系？

回过头看，这个电价项目的结构和所有那些经典的 AI Agent 是同一个模式：

> **一个从数据中学会了感知与决策的模型 + 一个定义了行动空间和约束的环境 = 一个能干活的 Agent。**

我的 GBDT 模型就是那个"学会了行动的智能体"。它通过历史天气和电价数据，学会了感知环境状态（当前天气 → 预测电价），并据此做出行动（买入或卖出）。而那个带有储能约束的优化环境，就是 Harness——它没有赋予模型任何智能，只是给了模型一个可以施展能力的舞台。

**Agency——那个感知、推理、行动的能力——来自模型训练，而不是来自外部代码的编排。**

我不需要写一大堆手工规则告诉模型"下雨天电价会跌"或者"夏天高温电价会涨"。这些模式，模型自己从数据里学到了。我要做的只是给它一个可以行动的框架。

这就是为什么我深信：**模型是驾驶者，Harness 是载具。** 缺了模型，载具是个空壳；缺了 Harness，模型无处施展。两者合在一起，才是一个完整的、能解决实际问题的 Agent。

## 什么不是 Agent？

明确了什么是 Agent 之后，我们非常有必要聊聊**什么不是 Agent**。

"Agent" 这个词，现在已经被一整个"提示词水管工（Prompt Plumber）"产业给劫持了。

看看市面上的那些东西：拖拽式工作流构建器、无代码 "AI Agent" 平台、各种复杂的提示词链编排库。它们共享着同一个幻觉——以为把 LLM 的 API 调用，用无数的 if-else 分支、节点图、硬编码的路由逻辑串联在一起，就算是"构建 Agent"了。

但那根本不是 Agent。那只是一个过度工程化的、极其脆弱的**过程式规则流水线**。在这些系统里，LLM 只不过是被生硬地楔进去，当成了一个美化过的文本补全器。

这帮"提示词水管工"试图通过无底线地堆叠过程式逻辑来暴力模拟智能——构造庞大的规则树、复杂的节点图、像瀑布流一样的链式提示词——然后双手合十，祈祷这些海量的"胶水代码"能涌现出某种自主行为，祈祷 LLM 的概率能力可以解决这些问题。

这完全是南辕北辙。

大模型的自主能力和涌现能力，**只来源于训练**。它能输出什么内容，完全取决于你提供的上下文以及模型本身在预训练和微调阶段获得的能力。你想通过死板的外部逻辑约束来"挤"出智能，在真正高标准、严要求的生产环境下是根本不可靠的。

所以这里就要回到我提出来的另一个内容：在我的库里面，**AI 本质是求解器，我们要做的本质是定义解空间，在解空间内让 AI 进行收敛**。这就是 LLM 大模型最大的意义——它是一个相对简单（相较于复杂的卷积神经网络结构）的、利用注意力机制（从它的名字 Transformer 就能看出来：变化、转置、相乘）的概率模型。所以我们使用补丁提示词的方式来处理，注定是脆弱的、不可泛化的。

这种伪 Agent 系统的致命伤非常明显：**脆弱、不可扩展、根本不具备泛化能力。** 

举个例子，这就像是几十年前流行过的"专家系统"或经典的符号 AI（GOFAI）。你试图穷举所有的条件和规则，一旦遇到规则之外的边缘情况（Edge Case），整个系统就会立刻崩溃。换个包装，喷上一层 LLM 的漆，依然改变不了它本质上是一个不可靠的符号规则系统的事实。

## 那么我们应该做什么？

所以话说回来，我们到底是在做 Agent 开发还是在做 Harness 开发？当一个人说 "我在开发 Agent" 时，他只可能是两个意思之一：

1. **训练模型**。通过强化学习、微调、RLHF 或其他基于梯度的方法调整权重。收集任务过程数据——真实领域中感知、推理、行动的实际序列——用它们来塑造模型的行为。这是 DeepMind、OpenAI、腾讯 AI Lab、Anthropic 在做的事。这是最本义的 Agent 开发。
2. **构建 Harness**。编写代码，为模型提供一个可操作的环境。这是我们大多数人在做的事。

**Agent 跨领域泛化，而 Harness 因领域而变。** 编程 Agent 的 Harness 是它的 IDE、终端和文件系统；自动驾驶的 Harness 是传感器阵列和汽车的物理执行性能；我那个电价预测项目的 Harness 则是带有储能约束的优化交易环境。Harness 的本质，就是为模型提供对特定外部环境的**感知接口与可操作执行模块**。

### Harness 工程师到底在做什么？

如果你在读这个系列，你很可能也是一名 Harness 工程师——这是一个极其强大的身份。既然明确了我们是在搭建环境而不是训练模型，那么以下才是你真正的工作核心：

- **实现工具**：给 Agent 一双手。文件读写、Shell 执行、API 调用、浏览器控制、数据库查询。每个工具都是 Agent 在环境中可以采取的一个行动。设计它们时要做到：原子化、可组合、描述清晰。
- **策划知识**：给 Agent 领域专长。产品文档、架构决策记录、风格指南、合规要求。要按需加载，不要前置硬塞。Agent 应该知道有什么可用，然后在需要时自己拉取所需。
- **管理上下文**：给 Agent 干净的记忆。通过子 Agent 隔离防止噪声泄露；通过上下文压缩防止历史信息把模型淹没；通过任务系统让目标持久化到单次对话之外。
- **控制权限**：给 Agent 明确的边界。沙箱化文件访问，对破坏性操作要求人工审批，在 Agent 和外部系统之间实施信任边界。这是安全工程与 Harness 工程的交汇点。
- **收集任务过程数据**：Agent 在你的 Harness 中执行的每一条行动序列都是宝贵的训练信号。真实部署中的感知-推理-行动轨迹，正是微调下一代 Agent 模型的原材料。你的 Harness 不仅仅是在"服务"当前的 Agent，它更是在帮助"进化"未来的 Agent。

## 为什么要写这个系列？

正因为在自己的项目中体验过"模型 + 环境"这个组合的威力，我开始对那些真正顶级的 Agent 系统产生了强烈的好奇：它们的 Harness 到底是怎么设计的？模型和环境之间的接口是怎么定义的？工具调用、状态管理、错误恢复这些工程细节，高手们是怎么处理的？

所以有了这个系列—— **Harness（广泛学习各大开源项目记录）**。

我为什么要深度学习？为什么是 **Claude Code**？因为 Claude Code 是我们所见过的最优雅、最完整的 agent harness 实现，本质上是一种 runtime。它展示了当你信任模型、把工程精力集中在 harness 上时会发生什么。

我会把优秀的开源 Agent 代码仓库拿过来，逐行逐句地阅读，写下我最真实的学习感受。不是转述别人的总结，不是复读论文的摘要，而是我自己一行一行读完代码之后的理解和思考。

我的电价项目用一个简单的 GBDT 就让我看到了"模型 + 环境"的力量。现在，我想看看当模型变成 GPT、Claude、Gemini 这样的大语言模型，当环境变成 IDE、终端、浏览器、整个互联网的时候，那些最优秀的工程师是怎么搭建 Harness 的。
