# Agent 的构建

> **参考文献**：Anthropic《Building Effective Agents》—— Erik Schluntz、Barry Zhang，2024-12-19，[原文](https://www.anthropic.com/engineering/building-effective-agents)

---

## 为什么需要 Agent

LLM 的 Transformer 架构本质上是一个概率分布问题——通过矩阵乘法建立 token 之间的关联，输出的永远是"下一个最可能的 token"。这意味着它天然擅长处理模糊的、需要判断的、没有唯一正确答案的事情。

而 workflow 是确定性的。写代码的时候步骤就定死了，不需要概率，不需要判断。

所以分界线其实很简单：**当一个固定流程没办法 cover 所有情况的时候，才需要 Agent。** Agent 的价值不在于"更高级"，而在于它能在运行时根据中间结果自己决定下一步。这恰好是 LLM 概率本质的用武之地。

反过来说，如果任务每次步骤都一样、完全可预测，那拉一个 Agent 进来只会引入不必要的不确定性——模型可能选错工具、绕远路、甚至瞎编。能确定的事情，就别交给概率。

一句口诀：**能用脚本解决的别用 workflow，能用 workflow 解决的别用 agent。**

## 这篇文章让我记住的几个点

### 1. 从简单到复杂，逐级递进

文章给出了一条很清晰的复杂度阶梯：

```
单次 LLM 调用 → prompt chaining → routing → parallelization → orchestrator-workers → evaluator-optimizer → full agent
```

每一级都有明确的适用条件。不是说 agent 就比 workflow 好——是说你应该从最简单的那一级开始，只有当它不够用的时候才往上走一级。这种"能不加复杂度就不加"的态度贯穿全文。

我觉得这个思路不只适用于 agent 设计，做任何系统设计都是这样：先用最笨的方案跑通，再看哪里不够用，再加东西。

### 2. Prompt chaining 是一个很实用的中间地带

当任务可以被干净地拆成固定子任务时，prompt chaining 就够了——步骤是固定的（像 workflow），但每一步内部用 LLM 来处理模糊性（像 agent）。中间还可以加程序化的 gate 来检查流程是否跑偏。

这让我意识到很多时候我们不需要一个"完全自主"的 agent，只需要一条链，每个环节让模型做一件小事就行。比如"先生成大纲 → 检查大纲是否合格 → 再基于大纲写正文"，这就是 prompt chaining，不是 agent。

### 3. 站在模型的角度设计工具

这是全文对我触动最大的一个观点：

> 站在模型的角度想问题。仅凭描述和参数，使用这个工具是否显而易见，还是需要仔细琢磨？如果需要琢磨，那对模型来说很可能也是如此。

以前设计 API 我想的是"人怎么用"。现在多了一层——"模型怎么用"。模型没有你脑子里的上下文，它只能靠你写的那几行描述来决定要不要用这个工具、怎么用。所以工具的命名、描述、参数设计，本质上就是在给一个"什么都不知道但很聪明的新人"写文档。

文章还提到一个具体的例子：他们在做 SWE-bench 的 agent 时，发现模型用相对路径的工具会出错（因为 agent 可能已经切换了目录）。解决方法是把工具改成只接受绝对路径——模型就再也没出过错。这种"防呆设计"（poka-yoke）的思路很有意思：不是教模型怎么用对，而是让工具本身变得不可能用错。

### 4. ACI 和 HCI 是一回事

文章提出了一个概念：Agent-Computer Interface（ACI），对标 Human-Computer Interface（HCI）。意思是你在人机交互界面上花多少心思，就应该在"模型-计算机接口"上花同样多的心思。

这个类比很精准。我们花了几十年研究怎么让界面对人友好，现在同样的问题换了一个用户——模型。模型不会看 UI，但它会"看"工具的定义、参数名、描述文本。这些东西的设计质量，直接决定了 agent 的表现上限。

### 5. Agent 的实现其实很简单

文章有一句话让我意外：

> 智能体能够处理复杂任务，但其实现往往很直接。它们本质上通常只是 LLM 在一个循环中基于环境反馈使用工具。

也就是说，agent 的核心就是一个 while 循环：观察环境 → 模型决定下一步 → 执行工具 → 拿到结果 → 再观察……直到模型认为任务完成。复杂的不是循环本身，而是工具设计和护栏设计。

## 发散：这篇文章让我想到的

### 框架是双刃剑

Anthropic 对框架的态度很微妙——他们承认框架能帮你快速起步，但同时警告说框架会"掩盖底层的提示词和响应，使调试更加困难"，还会"诱使你在更简单的方案就足够的情况下去增加复杂性"。

这让我想到一个更普遍的规律：**任何让你"不用理解底层"就能跑起来的东西，都会在你需要调试的时候反噬你。** 框架省掉的不是复杂度，是你对复杂度的理解。当事情顺利的时候这没问题，但 agent 系统偏偏是那种"经常不顺利"的东西——模型会犯错、会绕路、会卡住。这时候你必须能看到底层发生了什么。

所以他们的建议是"从直接调 API 开始"。我觉得这个建议的本质是：**先理解原理，再用工具。** 不是说框架不好，是说你得先知道框架帮你做了什么，才能在它出问题的时候知道去哪里找原因。

### 信任是一个渐进的过程

文章说 agent 适用于"你必须对它的决策有一定程度的信任"的场景。但信任不是一个开关——不是"信"或"不信"，而是一个一决断变化。

也许正确的做法是：**从最小的信任开始，逐步放权。** 先让 agent 做一件很小的事，验证它能做对；再让它做两件事；再让它自己决定做几件事……每一步都在积累信任。而不是一上来就把一个大任务整个甩给它。

这也解释了为什么 prompt chaining 是一个好的起点——它本质上就是"我只信任你做一步，做完我检查一下，再让你做下一步"。

### 错误会累积

文章提到 agent 的"错误累积（compounding errors）"问题。每一步的小偏差，经过多步之后可能变成大偏差。这跟控制论里的概念很像——开环系统（没有反馈）的误差会无限放大，闭环系统（有反馈）才能自我纠正。

所以 agent 设计里的"ground truth"概念很关键：每一步都要从环境拿到真实反馈（工具调用结果、代码执行结果），而不是让模型在自己的想象里越走越远。这也是为什么"沙箱测试"和"最大迭代次数"这些护栏不是可选的，而是必须的。

## 我的结论：没有评分系统的 Agent 不是好的 Agent

读完这篇文章，结合上面所有的思考，我得出一个自己的判断：**Agent 设计的关键应该有评分机制。**

为什么这么说？把前面几个点串起来看：

- Agent 的本质是一个循环，每一步都在做决策。但决策质量怎么衡量？如果没有评分，agent 自己不知道这一步做得好不好，你也不知道。
- 错误会累积。如果每一步都没有一个量化的"这步做得怎么样"的反馈，小偏差就会悄悄叠加成大偏差，等你发现的时候已经跑偏很远了。
- 信任是渐进的。你凭什么逐步放权给 agent？凭感觉吗？不行。你需要一个分数——它在过去 100 次决策里做对了多少次，哪类任务它得分高、哪类低。有了这个，"信任"就不再是主观判断，而是有数据支撑的决策。
- 文章里的 evaluator-optimizer 模式，本质上就是一个内置的评分系统——一个模型打分，另一个模型根据分数改进。但我觉得这个思路不应该只是一种"可选的工作流模式"，而应该是**所有 agent 的标配基础设施**。

具体来说，我认为一个好的 agent 评分系统至少要回答三个问题：

1. **这一步做得对不对？**（单步评分）—— 每次工具调用之后，有没有达到预期效果？
2. **整体任务完成得好不好？**（终局评分）—— 最终结果跟用户的期望差多远？
3. **历史表现怎么样？**（累积评分）—— 这个 agent 在同类任务上的成功率是多少？哪里是它的弱点？

没有评分，agent 就是一个黑箱——你不知道它为什么做了这个决定，不知道这个决定好不好，也没有数据来改进它。有了评分，你才能做到：发现问题、定位原因、迭代改进。这跟软件工程里"没有监控的服务不是好服务"是一个道理。

---

## 人类是关键链路：我们自己要提升的是决断能力

文章反复强调一个点：agent 在检查点处或遇到障碍时会暂停，等待人类反馈。人类不是被 agent 替代的对象，而是整个系统里的一个**关键链路**。

这让我意识到一个问题：如果人类是关键链路，那人类自己的能力就是整个系统的瓶颈。具体来说，agent 暂停下来问你"接下来怎么办"的时候，你得能快速、准确地做出判断。这个能力就是**决断能力**——在信息不完整的情况下，快速评估局面、做出选择、承担后果。

Agent 越强，留给人类的决策就越难（因为简单的它自己就做了）。这跟 Bainbridge 的"自动化反讽"是一个道理：自动化把容易的事做了，留给人的全是难的、罕见的、关键的。所以我们不能因为有了 agent 就放松，反而要刻意训练自己在关键节点上的判断力。

## 综上：我理解的 Agent 完整循环

把前面所有的思考串起来，我认为一个完整的 agent 应该是这样运作的：

```
输入（用户指令）
    │
    ▼
┌─────────────────────────────────┐
│  模型思考：理解任务，规划下一步    │
│         │                       │
│         ▼                       │
│  行动：工具调用                   │
│         │                       │
│         ▼                       │
│  返回：拿到工具执行结果            │
│         │                       │
│         ▼                       │
│  继续观察：评估当前状态            │
│         │                       │
│         ▼                       │
│  判断：任务完成了吗？              │
│    │              │             │
│   没完成          完成           │
│    │              │             │
│    └──→ 回到"思考" │             │
└─────────────────────────────────┘
                    │
                    ▼
          评分：结果过关吗？
            │           │
          过关        不过关 → 回到循环继续改进
            │
            ▼
      人类审查：确认最终结果
            │           │
          通过        打回 → 带反馈回到循环
            │
            ▼
        最终输出
```

关键点在最后两步：

1. **评分过关** —— 不是模型自己说"我做完了"就算完了，要有一个独立的评分机制来验证质量。
2. **人类审查** —— 评分过关之后，人类做最终确认。人类不需要参与每一步（那就变成 workflow 了），但必须在终点把关。

这个设计的好处是：循环内部 agent 是自主的（保持灵活性），但出口处有双重门槛（保证质量和可控性）。agent 的自主性和人类的控制权不是矛盾的——它们作用在不同的环节上。

## 还没想明白的

- Prompt chaining 要求任务能"干净地拆成固定子任务"。但实际中，怎么判断一个任务拆得够不够干净？拆不干净的时候，是硬拆还是直接上 agent？
- 工具的"防呆设计"听起来很好，但会不会过度限制工具的灵活性？绝对路径确实不会出错，但有些场景下相对路径更自然——这个平衡怎么找？
- 文章说"在受信任的环境中扩展任务规模"。那不受信任的环境呢？比如面向用户的场景，agent 可能被恶意输入诱导——这块没展开讲。
